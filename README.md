# AGHR：让模型把复杂任务做完、做对的预设与技能

AGHR 全称「自适应粒度人机协同求解」，是给 dsh 的一个中文预设，外加一份配套技能。它要回答的是同一件事：**面对一道难题，什么时候让模型直接算，什么时候该拆，拆到哪一层，拆开以后每一步怎么验。**

（预设是 dsh 新建会话时选的运行模式，决定这个会话里模型能用哪些能力、按什么分工干活。换预设等于换一套工作配置。）

作者是个人开发者，做它的原因很具体：一次性要模型给出完整答案，翻车率太高，而且翻了车还不容易发现。

用起来三步：把包装进 dsh、新建会话时选「AGHR 团队（中文）」、需要时点名技能。细节在后面「怎么用」一节。

## 背景：一个反复出现的翻车模式

起点是作者自己做数学题、研究生教材题、工程计算和多步代码任务时的经历。一次性把题丢过去要完整答案，出问题的方式不是「算错」，而是更难查的几种：跳步，中间步骤不写直接给结论；隐含假设不说，某个条件其实是猜的却没标出来；错误往后传，第三步错了，后面在错的前提上继续推，最后给出一个自洽但错误的答案；结果没法核验，除了「看着像」，没有别的检查手段。

第二个观察是提示词里的噪音。模型厂商会往系统提示里塞「回答快一点」「用简单的话说」「输出长思维链」这类要求。作者的原话是：这对能力本就不强的模型是灾难性干扰和降智——像把人一直放在高压环境里，再强的数学家也难无错算完一道微积分。AGHR 的应对是给模型一个干净的上下文和一份可照做的流程，而不是继续往提示词里加压。

第三个观察是作者当时的一手试验，不是可复现的基准：用 deepseek v4.1 flash 一次性求解会产生明显幻觉和错误解法；把问题拆成阶段、逐段提问之后，同一个参数量不高的小模型也能一步步走，结果接近更强的模型。这只说明「拆开对这个小模型这次有用」，不构成任何性能结论。

顺着这三个观察，作者还有一个判断：一味追求省 token，在模型能力继续变强的某个阶段之后会付出更大代价——通用思维能力被压住，退化到提示词也修不回来。所以 AGHR 不是省钱的取向，它优先的是「任务做完、结果站得住」。

## 它解决什么问题

把「拆不拆、拆到哪、怎么验」从经验判断变成一套可执行、可复查的流程：

- **先探测再决定。** 拿到任务先花最低成本问四件事：目标和约束是否明确、是否混了几种性质不同的工作、有没有没确认的关键假设、结果有没有合适的验证方式。四个答案决定走哪条路——直接求解、自适应拆分、先跟人澄清，还是升级处理或保留不确定性。
- **按认知难点拆，不按字数或固定步数拆。** 拆到哪一层由「这一步难在哪、错了能不能发现」决定，不追求各节点难度相等，也不为了流程好看强行走完全部阶段。
- **让错误在累计过多之前被人接住。** 每个节点有明确的输入、输出和验收条件；关键位置用追问、补条件、局部复算、独立推导来干预，而不是等到最后才验总账。
- **验证不了就明说。** 每个重要结论必须带一个状态：通过验证、部分通过、证据不足、发现明确错误。无法验证的保留不确定性，不许把「流程走完了」「程序跑通了」「审计通过了」当成「结论对了」。

## 怎么解决：方法、团队、落地

### 一层是方法，写在技能里

先探测再决定粒度，按认知难点拆分，再用两套标记控制错误传播：

- **可验证性分类 V1–V5。** 标每个节点「能不能验、用什么验」：可以跑程序或精确计算验的（V1）；能查不变量、边界、量纲但不能证明整体对的（V2）；靠来源、交叉证据、独立推导评估的（V3）；只能由人判断、涉及取舍的（V4）；当前根本没有可信手段的（V5）。这是方法内部的分类，不是行业标准，也不是难度分级。
- **验证状态。** 每个重要结论落成四种之一：通过验证、部分通过、证据不足、发现错误。

V4 和 V5 仍然可以用这套流程组织信息、管理假设、标出风险，但流程做完不等于结论正确。

拆分也不是越细越好。当输入和目标已经明确、只剩一个主要目标、关键依据能完整表达、并且有与风险相称的验收方式时，就该停手；建立不出有效验证手段时，靠继续拆是拆不出可靠性的——这时应该换验证方案、降低结论强度，或者干脆保留不确定性。

#### 出错之后怎么办：先分类，再动手

验证没过，不许直接重来一遍。技能里先把失败分成七类：理解错需求、假设不成立、推导错、算错或工具执行错、证据不足或来源冲突、验证器自己有问题、当前无法可靠解决。每类对应不同动作——理解错就重新澄清；假设错就补条件或停掉这条路线；推导错就退回到受影响的节点；算错就修实现重算；证据错就补证或交叉核对；验证器有问题就先审验证方法再决定要不要重新验收；无法解决就停止无效循环、披露不确定性并升级。

回退只退到受影响的节点和它的下游，不去推翻已经验证过、且不受影响的结果。同一节点认真修过两次还不行，原则上停止自动重试，重新评估路线、验证能力和资源。另外，反复生成不同答案不算独立验证。

#### 一个具体的例子

拿一道教材级数学题来说，「多阶段」在技能里是这个形状，不是固定五步，而是按这道题的认知难点长出来的：

1. 题目解析：确认条件完整，没有把未知量当已知量用——比如题目没给导数值，就不能默认它为零。
2. 方法选择：确认选的方法和它的前置条件相容，不只是「这个公式眼熟」。
3. 完整推导：关键等式和每一步都要有依据，不只给结论。
4. 独立验证：能代回原方程就代回、能查量纲就查、能换一条互补路径就换。
5. 整合答案：检查结论完整，且与前面已确认的结果一致。

每一步都能被检查，才轮得到下一步；某一步验不过，就回到那一步，而不是继续往后写。

### 二层是团队，装在预设里

预设装了四职责位，每个只做一段：

| 职责位 | 管什么 | 不管什么 |
| --- | --- | --- |
| Leader | 对接用户，提取目标、约束、交付格式，把任务交给 Planner，对最终交付负责 | 不亲自包办全部技术工作，也不能凭「流程完整」就认定结果正确 |
| Planner | 拆任务、定义节点输入输出与验收标准；接到审计报告后决定推进、局部修正、重规划还是停 | 不替 Operator 干活，也不替 Validator 出审计结论 |
| Operator | 实际执行：推导、计算、写代码、查资料、跑检查；如实报告失败与缺失条件 | 不补造前提，不把没跑的检查说成已验证 |
| Validator | 只做事后审计：按既定验收条件报告通过、未通过或无法判断，并给出对应证据 | 不改验收标准，不修结果，也不决定是否回退 |

**为什么执行和审计必须分开**：模型的自我确信不是证据。同一个执行者兼任审计时，两边共享同一套错误假设、同一套推导、同一套验证逻辑，验证就退化成把自己的结论再说一遍——换成第二个执行者或第二个模型也不自动构成独立验证。Validator 只认验收条件和实际证据，不认执行者的自述。

### 三层是落地：一个预设、一份技能、一页说明

选上预设，你得到一个按上面分工干活的会话；技能给模型一份可以照着走的流程；Plugins 页里的这一页只是把「这是什么」讲清楚。三者不互相替代：没有技能，团队知道要分工但不知道拆到什么粒度；没有预设，技能就只是一份文档。

## 什么时候它会停下来问你

不是每一步都来问。技能要求先判断「这个问题会不会实质改变结果」，会才问。需要人介入的情形分五种：澄清意图、补缺失资料、纠正推理错误、做方案取舍、做专业审查。

它还会记账：记下人介入了几次、是哪一类。因为在统计「模型自己做到了什么」时，人给的资料、人的纠错、人的专业判断都不能算成模型的能力——这一点会写进交付里。

## 怎么用

1. **装上。** 三步：
   - 把包目录放到 dsh 的插件目录下，例如 `~/.dsh/plugins/dsh-plugin-aghr`；
   - 让 profile 装上它：`dsh plugin --profile web add link:/path/to/dsh-plugin-aghr`（已发布到 npm 时用 `dsh plugin --profile web add dsh-plugin-aghr`）；
   - 重启 dsh。升级与卸载的写法见 `CHANGELOG.md`。
2. **新建会话时选「AGHR 团队（中文）」。** 会话就按四职责位分工，Leader 对你，其余三个由它派活。
3. **需要它出场时点名技能。** 技能默认可用，模型自己会调；你也可以直接说「用 aghr 拆这个问题」，或者在任务属于「结果要能验」的类型时提前点名——教材级数学题、工程计算、多步代码改动、多来源核查。

## 边界与代价

**适合**：结果需要能验、错了代价高的任务——教材级题、工程计算、要改动的代码、要多方核对的材料。
**不适合**：闲聊、润色、要一次成型的小活——那些场景下这套流程只是增加开销。

- **不省 token。** 这是「宁可多花也要把事做完」的取向，比别的预设更费上下文和时间。想要极简、快速、一次到位的回答，别用它。
- **长工具输出会被裁。** 从 0.5.0 起，会话里 `bash`、读文件这类工具产出的长文本会被裁掉中间一段，只留开头和结尾；上下文增长变慢、压缩来得更晚，代价是模型看到的中间部分变短。不想要这个行为，按 `CHANGELOG.md` 里写的方式去掉那一项。
- **V4、V5 的结论只能保留不确定性。** 涉及取舍、偏好、专家判断或缺少验证手段的节点，流程结束时给你的仍然是「证据不足」或「部分通过」，不会自动变成确定的答案。
- **依赖中文预设。** 分工和表达纪律是按中文写的，换其他语言的会话效果没验过。
- **它管不到的事。** 模型情绪、语气、是否愿意配合，不在这个技能的范围里。

## 常见问题

**会不会很慢？** 会比一次性求解慢，也可能多花几倍 token。它换的是「错了能不能当场发现」，不是速度。

**能只装技能、不选预设吗？** 能。技能的流程对任何会话都成立，只是少了四职责位的分工和那段事后审计。

**和写更好的提示词有什么区别？** 提示词解决「这一次说清楚」，这里解决「错了在哪一步被抓住、验不了的怎么标出来」。提示词越写越长本身也会变成新的噪音。

**为什么是中文？** 团队分工和表达纪律是按中文语境写的，作者自己也在中文里用。
